# PhantomProbe

最近在开发安卓虚拟机软件（它需要同时保活几十个以上的子进程）
Android 12 起，系统会对子进程进行回收，而虚拟机app想判断用户是否已解除这个限制是很麻烦的，但也不能因为麻烦就不进行任何检测单纯让用户自行判断，那样显然很不优雅🤔
由于安卓系统没有任何一个不提权（root / adb）就能读取子进程限制状态的公开API，厂商还可能改开关名称或位置
所以我做了这样一个小项目来对子进程状态进行检测
它的原理目前也用在了我的虚拟机软件中


## 背景

Android 12（API 31）起，ActivityManager 限制单个应用可同时保活的非沙箱子进程数。AOSP 默认 32个，上限与开发者选项开关只在 root / adb 侧可见，普通应用无法可靠读取。失败是静默的：进程被回收时没有回调，表现为别处的崩溃或黑屏。


## 进程拓扑

| 进程 | `android:process` | 职责 |
| --- | --- | --- |
| 宿主 | 默认 | Compose UI、view model，每次运行仅一次 `startService`。不 fork，不 wait。 |
| 探测 | `:phantom` | 状态机：fork、触发、轮询、回收、上报。 |
| 握手 | `:probe` | 仅改变应用进程集合，随后退出。 |

宿主与探测进程通过 `ResultReceiver` 通信。上报只含数字与枚举，用户可见字符串全部在 UI 层解析，因此 UI 支持五种语言，探测层不依赖资源。

## 为什么 fork 不能留在 UI 进程

`fork()` 复制页表时以写方式持有地址空间的 `mmap_lock`；UI 线程每次内存分配都要以读方式获取同一把锁，因此必须等待。66 次 fork 在当前硬件上约 300 ms，Compose 每帧都会分配，所以同样的探测在 View 体系中不明显，在 expressive 界面上直接表现为卡顿。

`mmap_lock` 属于地址空间而非线程。降优先级、分批 fork、批次间休眠，都只是把总耗时摊到更多帧上。换进程是唯一有效解法。

## 界面

Material 3 Expressive

## 说明

* Android 12 及以上有效，更低版本报“不适用”
* “未观察到回收”是对本次运行的观察，60 秒观察窗口可用于在后继续发现被回收后更新最新的状态。
